A

接着 EAGLE：DSpark 到底解决什么问题？

EAGLE 已经减少了目标大模型的串行调用。 但草稿模块自己仍要逐步运行 Transformer。 DSpark 进一步压缩草拟阶段的串行计算。

方法 草稿骨干怎样运行？ 新采样 token 怎样影响后续？ 主要取舍
EAGLE-3 随草拟步骤重复前向 喂回草稿内部状态与 token 有依赖，但草拟有串行成本
DFlash 一次前向处理整块 同块实际采样结果不再反馈给骨干 草拟并行，但后缀容易不协调
DSpark 一次前向处理整块 轻量 Markov 或 RNN 头顺序修正 保留并行计算，补充块内依赖

这里的“半自回归”有明确边界。 骨干不跟着新 token 重跑；输出头仍按顺序采样。 DSpark 通常提出一条候选链。 它不要求像 EAGLE-2 那样构造候选树。

参考：NVIDIA 对 DSpark 架构的说明。

Confidence head：它预测的不是词表概率

草稿分布 qₖ 回答“下一个 token 选谁”。 置信度 cₖ 回答“前缀都通过时，这一步预计能否通过”。 它是一个接收率估计，不是目标模型的最终裁决。

调度器：为什么不把所有草稿都送去验证？

连续接收只能保留前缀。 后面的 token 再可信，也必须等前面的都通过。 因此调度按累计生存概率 aⱼ 排序。

请求 各位置条件置信度 c 各前缀生存概率 a
A 0.90 / 0.90 / 0.20 0.90 / 0.81 / 0.162
B 0.60 / 0.90 / 0.90 0.60 / 0.54 / 0.486

若只有两个额外验证名额，优先选 A₁、A₂。 虽然 B₂ 的 c₂=0.9，它的 a₂ 只有 0.54。 不能只按单位置 c 值挑选。 累计概率沿请求单调不增，排序能保留前缀关系。

预算本身也要算收益，而不是固定为两个。

论文的 early-stop 与源码的 argmax 为什么不同？

论文基础算法在预计吞吐不再增加时停止。 当前块的后续置信度依赖已采样 token。 回看整块再选最优截断点，可能引入选择偏差。 工程方案用滞后历史选预算，隔开当前采样结果。 因此可扫描硬件曲线中的多个峰值。

论文生产方案使用前两步的置信度来估计预算。 本地 HostConfidenceBudgetPlanner 实现了相应历史路径。 实际滞后还取决于流水线与 carry 配置。 这不是把“前两步历史”误当成当前 token 的精确质量。

源码：历史预算、当前分配。 论文依据：DSpark §3.2.2 与 §5.2。

假设草稿是 E F G H，调度只选 E F G。 目标确认 E、F，在 G 处拒绝并产生 G*。 下一轮以 G* 为 anchor。 H 没有获得验证名额，也不会进入最终输出。 这是流程示意，token 字母不代表真实分词。

要观察的量 为什么重要？
草稿整轮耗时 并行骨干仍有固定开销
平均实际接收长度 γ 大不代表确认得多
每请求验证长度与总 batch tokens 调度是否节省目标计算？
置信度校准误差 高估会浪费验证，低估会少推进
每用户速度和总吞吐 单请求收益不代表高并发收益
compact 与 graph 档位 动态长度是否真正减少物理计算？

静态模式可以跳过动态置信度调度。 因此“用了 DSpark 草稿”不等于“完整启用了收益调度”。 低接收率时，前面整块草拟的成本无法追回。 默认参数和性能要结合目标模型、硬件与负载判断。
